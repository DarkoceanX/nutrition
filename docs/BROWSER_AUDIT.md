# Браузерная проверка сайта «В своём ритме»

Дата: 1 ноября 2026 года. Проверен существующий сайт из `nutrition-site/dist/` через локальный HTTP-сервер и настоящие браузеры. Превью запущено во вкладке «Результат» VibeForge. Содержимое страницы, её стили и обработчики не менялись; контрольные суммы проверенных файлов сохранены в [results.json](../review/browser/results.json).

**Результат: обычные сценарии работают, но готовность к публичному выпуску не подтверждена.** В каждом браузере прошли 19 из 26 групп проверок. Всего: 38 успешных групп, 14 неуспешных. Это две группы проблем: отправка полей формы на сайт при отказе JavaScript и недостаточный контраст текста. Число 14 учитывает повторение одной проблемы разными способами и в двух браузерах, а не четырнадцать независимых дефектов.

## Подтверждённые проблемы

### BR01 — P1: поля уходят в URL при отказе JavaScript

Место: `nutrition-site/dist/index.html`, форма `#booking-form`; перехват отправки находится только в `nutrition-site/dist/app.js`.

Воспроизведение: отключить JavaScript либо заблокировать загрузку `app.js`, ввести тестовое имя, выбрать тему, указать тестовое время и нажать «Подготовить письмо» или Enter. Браузер выполняет GET-запрос на главную с параметрами `name`, `topic`, `time`. Пример структуры: `/?name=Тест&topic=Питание…&time=Тестовое+время`. Фактические URL и методы запросов сохранены в случаях `F-*` в `results.json`.

Это противоречит безусловному тексту окна «О ваших данных» о том, что поля не передаются серверу. Они могут оказаться в истории адресов и технических журналах хостинга. Использовались только искусственные данные; наличие или содержимое журналов публикации не исследовалось.

Исправление по WEB02/T05: форма должна становиться доступной только после успешной инициализации обработчиков. При отказе нужен понятный запасной путь с прямым контактом. Защитить и кнопку, и отправку клавишей Enter; смены метода на POST недостаточно. Затем повторить все случаи `F-*` в обоих браузерах.

### BR02 — P1: недостаточный контраст смыслового текста

axe-core отметил 25 элементов на настольной странице в каждом браузере. Среди них есть текст карточек, пояснения формы и кнопка информации о данных. Примеры измеренных отношений:

| Элемент | Контраст |
| --- | --- |
| Текст второй карточки `.situation` | 4,16:1 |
| Подпись под фотографией | 4,23:1 |
| Пояснение о сведениях здоровья `.form-privacy` | 4,28:1 |
| Кнопка «Как используются данные» | 4,07:1 |

Для обычного небольшого смыслового текста нужен контраст не ниже 4,5:1. Чисто декоративные элементы оцениваются отдельно; автоматическое число 25 не следует трактовать как 25 отдельных подтверждений нормативного нарушения. [Пояснение W3C к SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

Исправление по WEB04: скорректировать семантические цвета текста в существующей палитре, проверяя каждый фон. После этого повторить автоматическую проверку и визуально оценить мелкие подписи. Результат axe не заменяет проверку со скринридером.

### BR03 — P2: мобильной навигации по разделам нет

При ширине до 800 пикселей `.desktop-nav` скрыта, альтернативного меню нет. Кнопка «Записаться» остаётся доступной, а остальные разделы находятся прокруткой. Это ограничение текущего интерфейса, а не отказ существующей кнопки. Стоит предусмотреть доступную навигацию по разделам в рамках BP08.

## Что изменено для проведения проверки

- `serve.mjs` использует назначенный порт, определяет `dist/` относительно своего файла и сообщает об ошибках запуска. Семь вариантов отсутствующего или неверного порта завершаются ожидаемым отказом; работающий сервер проверен из корня проекта.
- В `.vibeforge/workspace.json` записана команда запуска превью.
- Добавлены повторяемые сценарии `qa/browser/check.mjs` и `qa/browser/demo.mjs`, закреплены версии зависимостей и подготовка локальной среды.
- Сохранены результаты и демонстрационные материалы. Исправление BR01–BR03 в эту проверку не входит; файлы интерфейса остались прежними.

## Повторение проверки

Из корня рабочей копии:

```bash
sh qa/browser/setup.sh
# Только для Ubuntu 26.04 x64 без необходимых библиотек браузера:
python3 qa/browser/setup-linux-libs.py
node qa/browser/check.mjs
node qa/browser/demo.mjs
```

Сайт предварительно запускается механизмом превью VibeForge. Проверки используют `VIBEFORGE_SESSION_PORT` / `PORT`. Если среда команд их не передаёт, передать `--url` с фактическим адресом превью этой рабочей копии. Сами сценарии сервер не запускают. При найденных проблемах `check.mjs` возвращает код 1 и сохраняет подробный JSON; это ожидаемый сигнал о непройденных проверках.

Повторный запуск перезаписывает одноимённые результаты в `review/browser/`. Для сравнения выпусков предварительно сохранять предыдущий комплект отдельно внутри рабочей копии. Браузерные бинарники, библиотеки, временные профили и кэш исключены из Git.

## Ограничения и дальнейшие действия

Проверена локальная версия сайта. Доставка письма, установленное почтовое приложение посетителя, реальная запись на консультацию, публичные доступы и работа опубликованной версии не проверялись; внешних сообщений и публикаций не выполнялось. Safari/WebKit, физические iOS/Android, скринридеры и настоящий масштаб браузера через Ctrl+Plus не проверены. Эмуляция 720 × 450 подтверждает перестроение интерфейса, но не подменяет эти испытания. Время загрузки на локальном сервере не характеризует скорость публичного сайта.

Следующая техническая очередь: исправить BR01, затем BR02, принять решение по BR03 и повторить проверку. После допуска к выпуску отдельно выполнить T09–T10 и T12 из [ТЗ](TECHNICAL_SPEC.md): подтверждение доставки и обработки обращения, внешнюю проверку публикации и восстановление предыдущей версии. Содержательные задачи бренд-протокола остаются в [плане внедрения](IMPLEMENTATION_PLAN.md).
