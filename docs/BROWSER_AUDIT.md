# Браузерная проверка сайта «В своём ритме»

Дата: 1 ноября 2026 года. Проверен существующий сайт из `nutrition-site/dist/` через локальный HTTP-сервер и настоящие браузеры. Сервер превью запущен, однако доступ пользователя во вкладке «Результат» через SSH пока не восстановлен. Содержимое страницы, её стили и обработчики не менялись; контрольные суммы проверенных файлов сохранены в [results.json](../review/browser/results.json).

**Результат: обычные сценарии работают, но готовность к публичному выпуску не подтверждена.** В каждом браузере прошли 19 из 26 групп проверок. Всего: 38 успешных групп, 14 неуспешных. Это две группы проблем: отправка полей формы на сайт при отказе JavaScript и недостаточный контраст текста. Число 14 учитывает повторение одной проблемы разными способами и в двух браузерах, а не четырнадцать независимых дефектов.

### Автономный интерактивный просмотр

Скачайте [interactive-preview.html](../review/interactive-preview.html) (около 3,5 МБ) и откройте скачанный файл в браузере. Он содержит текущую страницу, стили, JavaScript и изображения. Для загрузки и просмотра сеть и SSH не нужны. Форма подготавливает письмо; его отправка требует почтового приложения и подключения к сети. Браузер может ограничивать доступ к буферу обмена — тогда сайт выделяет текст для ручного копирования.

Файл собран сценарием [export-preview.mjs](../qa/browser/export-preview.mjs). В [манифесте](../review/interactive-preview.json) сохранены время экспорта и SHA-256 исходников и результата. Экспорт переносит исходный скрипт в конец HTML, чтобы он выполнялся после создания элементов страницы. Снимок не обновляется автоматически; файлы в `nutrition-site/dist/` остались прежними.

Отдельная проверка [check-offline.mjs](../qa/browser/check-offline.mjs) открыла файл через `file://` в Chromium и Firefox с отключённой сетью: **14 групп из 14 пройдены**. Сравнены текст, элементы управления и выбранные вычисленные стили с HTTP-версией. Проверены три встроенных изображения, 11 ссылок, пять FAQ, четыре темы обращения, редактирование письма, почтовые ссылки с перехватом, оба диалога и их закрытие тремя способами. На ширине 320, 375 и 1440 пикселей горизонтального переполнения нет. Ошибок JavaScript и HTTP-запросов не зарегистрировано.

При обычном нажатии кнопки копирования Chromium предложил ручное копирование, Firefox сообщил об успешном копировании. В обоих браузерах отдельно проверено выделение текста после искусственного отказа буфера. Чтение буфера обратно в этой проверке не выполнялось. Результаты: [offline-results.json](../review/browser/offline-results.json), [снимок автономной версии](../review/browser/offline-desktop.png).

Исходные проблемы BR01–BR03 остаются в очереди исправлений. Результаты автономного просмотра дополняют полный аудит с 38 успешными и 14 неуспешными группами проверок.

### Доступ пользователя к превью

После проверки пользователь сообщил об отказе подключения к `127.0.0.1` во вкладке превью. Диагностика 1 ноября 2026 года в 16:36 UTC подтвердила: сервер запущен из этой рабочей копии, слушает `0.0.0.0:5601`; порт 5601 закреплён за текущей сессией. Главная, `app.js` и `styles.css` возвращают HTTP 200 при обращении с сервера. Эти проверки не подтверждают доступ с устройства пользователя.

Пользователь подтвердил подключение через SSH в приложении. Адрес `127.0.0.1` в браузере относится к устройству, на котором работает браузер. Для доступа к удалённому сайту можно использовать внешний IP с портом, предусмотренный VibeForge маршрут к превью или локальный SSH-проброс. Параметры проброса для этой сессии:

| Участок | Адрес |
| --- | --- |
| Вход на компьютере пользователя | `127.0.0.1:5601` |
| Соединение | Существующее SSH-подключение к серверу проекта |
| Назначение на сервере | `127.0.0.1:5601` |

В терминах OpenSSH параметр такого клиентского подключения — `-L 127.0.0.1:5601:127.0.0.1:5601`. Это описание маршрута, а не команда для запуска на сервере. Другой локальный порт допустим, если интерфейс VibeForge использует именно его. В следующих сессиях удалённый порт нужно брать из фактического назначения VibeForge.

Состояние проброса и полный адрес вкладки на клиенте недоступны для проверки из этой сессии, поэтому точная причина отказа на стороне клиента не установлена. Сервер повторно ответил HTTP 200 во время подготовки автономного файла. Инструментов управления клиентским SSH-подключением нет; запрошенная интеграция `vibeforge ssh` отсутствует в реестре. Повторный запуск работающего сайта не подтверждает исправления клиентского маршрута.

Открытие серверного сайта во вкладке пользователя остаётся незавершённой частью задачи. Автономный файл позволяет оценить текущий интерфейс без этого соединения. Публикация сайта в интернете и изменение общего сервиса VibeForge не выполнялись.

### Прямой адрес сервера и существующая публикация

Дополнительная проверка 1 ноября 2026 года в 16:59 UTC:

- На сетевом интерфейсе сервера назначен внешний IP `199.195.196.219`. Процесс сайта слушает `0.0.0.0:5601`.
- [Текущая рабочая версия на сервере](http://199.195.196.219:5601/) вернула HTTP 200 при запросе с самого сервера. SHA-256 ответа совпал с `nutrition-site/dist/index.html`: `8bcb421fdc47061a11073d1cdc92313fa33c3c84f31b70df96a3741c16f930e2`.
- Независимая проверка через веб-инструмент не состоялась: инструмент вернул `Unable to resolve open call due to invalid ref_id argument`. Это ошибка инструмента; по ней нельзя заключить, что входящий порт закрыт или сайт неисправен. Доступ с компьютера пользователя остаётся непроверенным.
- Через подключённый Sites проверена [прежняя публикация](https://nutrition-daily-rhythm.stonybox65.chatgpt.site): статус `active`, версия 1, один разрешённый пользователь с ролью владельца, внешних посетителей нет. Это отдельный размещённый экземпляр; его соответствие текущим файлам в этой проверке не устанавливалось. Нового развёртывания и изменения аудитории не было.

Для прямого просмотра серверной версии собственный домен необязателен. Он даёт сайту постоянное имя; доступность сервера и настройка HTTPS решаются отдельно. Адрес с портом 5601 относится к текущей сессии и зависит от работы её процесса. Если прямое внешнее соединение недоступно, закрытый просмотр через существующее SSH-подключение требует настройки клиентского проброса, описанного выше. Правила сетевой защиты, SSH-служба и общая инфраструктура в ходе диагностики не изменялись.

### Остановка и восстановление превью

Позднее пользователь подтвердил, что серверный адрес открывался, затем стал недоступен. Это подтверждает состоявшийся просмотр с его устройства, но не постоянную доступность.

1 ноября 2026 года в 17:26 UTC проверка `ss` не обнаружила слушающего процесса на порту 5601, запрос к `127.0.0.1:5601` завершился отказом соединения (`curl`, код 7). Отсутствие процесса подтверждает непосредственную причину текущей недоступности. Причину завершения предыдущего процесса установить не удалось: в проверенных записях сервиса VibeForge не найдено относящегося к нему сообщения.

Сайт восстановлен штатным запуском превью: `node nutrition-site/serve.mjs`. Новый процесс PID 34136 запущен VibeForge из текущей рабочей копии и слушает `0.0.0.0:5601`. Восстановление не потребовало изменения кода сайта, домена, SSH или правил сети.

После запуска проверены пять ресурсов по `127.0.0.1:5601` и `199.195.196.219:5601`: главная, CSS, JavaScript и оба изображения. Все десять запросов вернули HTTP 200; SHA-256 каждого ответа совпал с соответствующим файлом рабочей копии. [Результаты восстановления](../review/browser/server-recovery.json) содержат время, адреса и контрольные суммы. Проверки выполнялись с сервера; повторное открытие на компьютере пользователя после перезапуска ещё не подтверждено.

Текущий адрес обслуживает процесс превью сессии. Постоянное размещение с автоматическим восстановлением необходимо подготовить отдельно в рамках выпуска WEB05; подключение домена само по себе не поддерживает работу процесса.

## Подтверждённые проблемы

### BR01 — P1: поля уходят в URL при отказе JavaScript

Место: `nutrition-site/dist/index.html`, форма `#booking-form`; перехват отправки находится только в `nutrition-site/dist/app.js`.

Воспроизведение: отключить JavaScript либо заблокировать загрузку `app.js`, ввести тестовое имя, выбрать тему, указать тестовое время и нажать «Подготовить письмо» или Enter. Браузер выполняет GET-запрос на главную с параметрами `name`, `topic`, `time`. Пример структуры: `/?name=Тест&topic=Питание…&time=Тестовое+время`. Фактические URL и методы запросов сохранены в случаях `F-*` в `results.json`.

Это противоречит безусловному тексту окна «О ваших данных» о том, что поля не передаются серверу. Они могут оказаться в истории адресов и технических журналах хостинга. Использовались только искусственные данные; наличие или содержимое журналов публикации не исследовалось.

Исправление по WEB02/T05: форма должна становиться доступной только после успешной инициализации обработчиков. При отказе нужен понятный запасной путь с прямым контактом. Защитить и кнопку, и отправку клавишей Enter; смены метода на POST недостаточно. Затем повторить все случаи `F-*` в обоих браузерах.

### BR02 — P1: недостаточный контраст смыслового текста

axe-core отметил 25 элементов на настольной странице в каждом браузере. Среди них есть текст карточек, пояснения формы и кнопка информации о данных. Примеры измеренных отношений:

| Элемент | Контраст |
| --- | --- |
| Текст второй карточки `.situation` | 4,16:1 |
| Подпись под фотографией | 4,23:1 |
| Пояснение о сведениях здоровья `.form-privacy` | 4,28:1 |
| Кнопка «Как используются данные» | 4,07:1 |

Для обычного небольшого смыслового текста нужен контраст не ниже 4,5:1. Чисто декоративные элементы оцениваются отдельно; автоматическое число 25 не следует трактовать как 25 отдельных подтверждений нормативного нарушения. [Пояснение W3C к SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

Исправление по WEB04: скорректировать семантические цвета текста в существующей палитре, проверяя каждый фон. После этого повторить автоматическую проверку и визуально оценить мелкие подписи. Результат axe не заменяет проверку со скринридером.

### BR03 — P2: мобильной навигации по разделам нет

При ширине до 800 пикселей `.desktop-nav` скрыта, альтернативного меню нет. Кнопка «Записаться» остаётся доступной, а остальные разделы находятся прокруткой. Это ограничение текущего интерфейса, а не отказ существующей кнопки. Стоит предусмотреть доступную навигацию по разделам в рамках BP08.

## Что изменено для проведения проверки

- `serve.mjs` использует назначенный порт, определяет `dist/` относительно своего файла и сообщает об ошибках запуска. Семь вариантов отсутствующего или неверного порта завершаются ожидаемым отказом; работающий сервер проверен из корня проекта.
- В `.vibeforge/workspace.json` записана команда запуска превью.
- Добавлены повторяемые сценарии `qa/browser/check.mjs` и `qa/browser/demo.mjs`, закреплены версии зависимостей и подготовка локальной среды.
- Сохранены результаты и демонстрационные материалы. Исправление BR01–BR03 в эту проверку не входит; файлы интерфейса остались прежними.

```bash
node qa/browser/check-offline.mjs
```

Сайт предварительно запускается механизмом превью VibeForge. Проверки используют `VIBEFORGE_SESSION_PORT` / `PORT`. Если среда команд их не передаёт, передать `--url` с фактическим адресом превью этой рабочей копии. Сами сценарии сервер не запускают. При найденных проблемах `check.mjs` возвращает код 1 и сохраняет подробный JSON; это ожидаемый сигнал о непройденных проверках.

Для создания автономного HTML нужны только исходники сайта и Node.js. `check-offline.mjs` дополнительно требует установленный Playwright и работающий локальный сайт для сравнения; проверяемая копия открывается в отдельном контексте браузера с отключённой сетью. Перед испытанием сверяются контрольные суммы экспорта и исходников. Непройденные сценарии дают код завершения 1.

Повторный запуск перезаписывает одноимённые результаты в `review/browser/`. Для сравнения выпусков предварительно сохранять предыдущий комплект отдельно внутри рабочей копии. Браузерные бинарники, библиотеки, временные профили и кэш исключены из Git.

## Ограничения и дальнейшие действия

Проверена локальная версия сайта. Доставка письма, установленное почтовое приложение посетителя, реальная запись на консультацию, публичные доступы и работа опубликованной версии не проверялись; внешних сообщений и публикаций не выполнялось. Safari/WebKit, физические iOS/Android, скринридеры и настоящий масштаб браузера через Ctrl+Plus не проверены. Эмуляция 720 × 450 подтверждает перестроение интерфейса, но не подменяет эти испытания. Время загрузки на локальном сервере не характеризует скорость публичного сайта.

Следующая техническая очередь: исправить BR01, затем BR02, принять решение по BR03 и повторить проверку. После допуска к выпуску отдельно выполнить T09–T10 и T12 из [ТЗ](TECHNICAL_SPEC.md): подтверждение доставки и обработки обращения, внешнюю проверку публикации и восстановление предыдущей версии. Содержательные задачи бренд-протокола остаются в [плане внедрения](IMPLEMENTATION_PLAN.md).
